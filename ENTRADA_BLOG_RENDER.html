Manual de despliegue del proyecto RAVE / Aura Humana en Render.com: qué archivos viajan al servidor, cuáles quedan en la máquina local y qué límites tiene el plan gratuito.

RAVE es una aplicación Flask de Diseño Humano que hoy corre en local con INICIAR.cmd. Este manual explica cómo llevarla a la nube usando Render como hosting y, opcionalmente, Neon como base de datos.

1. Qué es cada pieza

  • Render: ejecuta el proceso Python y sirve la web.
  • Gunicorn: servidor de producción. En local se usa Waitress.
  • Neon (PostgreSQL): guarda cuentas y perfiles en la nube. Es opcional.
  • CSV del proyecto: puertas, canales, centros, cruces, perfiles. Son la base de cálculo.

2. Archivos que ya están preparados en el repo

Tres archivos hacen casi todo el trabajo:

render.yaml

services:
  - type: web
    name: diseno-humano
    env: python
    plan: free
    buildCommand: pip install -r requirements.txt
    startCommand: gunicorn app:app

Procfile

web: gunicorn app:app

requirements.txt

Flask>=3.0
pandas>=2.0
openpyxl>=3.1
gunicorn>=21.0
waitress>=2.1
pyswisseph>=2.10
reportlab>=4.0
Pillow>=10.0
psycopg2-binary>=2.9

La aplicación lee el puerto de la variable de entorno PORT (por defecto 5000), así que funciona igual en local y en la nube sin tocar código.

3. Qué sube al servidor y qué no

Regla simple: viaja el código y los datos públicos. Queda local todo lo personal y lo pesado.

Viaja:

  • Código: app.py, preparar_datos.py, bajar_fotos_publicas.py, nube_db.py, auth_db.py.
  • Plantillas: templates/*.html.
  • Datos públicos: puertas.csv, canales.csv, centros.csv, cruces.csv, lineas_popup.csv, perfiles.csv, definiciones.csv, tipos.csv, eneatipos.csv, doshas.csv, numerologia.csv, natal.csv, natal_planetas.csv, personas_publicas.csv, parejas_publicas.csv, fotos_publicas.csv.
  • Textos: canales_accesibles/, base_informe_ia.txt, canales simplificados.txt.
  • Esquemas SQL: schema_fase1.sql, schema_fase2.sql.
  • Config: render.yaml, Procfile, requirements.txt, .gitignore.

No viaja (queda local):

  • Datos personales: datos.csv, vinculos.csv, clan.csv, conocidos.csv, ia.csv, informe.csv.
  • Memorias personales: memoriaOC.md.
  • Página de laboratorio: templates/lab.html (por eso /lab da 404 en la nube).
  • Excel de trabajo: *.xlsx, con dos excepciones que la app usa en ejecución.
  • Medios pesados: static/canales_audio/ (91 MB), videos_canales/ (48 MB), Publicos/ (18 MB).
  • Secretos: .env.

4. Primer despliegue, paso a paso

  1. Repo privado en GitHub. Crear aura-humana como Private, sin README ni licencia, y agregarlo como remoto: git remote add origin <URL>.
  2. Subir el código. Doble clic en PUBLICAR.cmd (o git push -u origin main).
  3. Crear el servicio en Render. New → Web Service → conectar el repo. Render detecta render.yaml y completa solo el build y el start.
  4. Si no lo detecta a mano: build pip install -r requirements.txt, start gunicorn app:app.
  5. Variable de entorno. Solo si vas a usar cuentas: DATABASE_URL con la cadena de Neon.
  6. Deploy. Al terminar, revisar los logs y abrir la URL del servicio.

5. Neon: base de datos opcional

Sin DATABASE_URL la app funciona igual, todo en CSV, y las rutas de cuenta responden "Neon no configurado". Con la variable puesta:

  • Las tablas se crean solas al primer uso, desde schema_fase1.sql y schema_fase2.sql.
  • Fase 1: dispositivos y perfiles_nube (por navegador).
  • Fase 2: cuentas, sesiones y perfiles_cuenta (por correo).
  • En /cuenta se crea la cuenta, se suben personas y se bajan al navegador.

6. Límites reales del plan gratuito

  • El servicio se suspende por inactividad: el primer acceso después de un rato tarda en despertar.
  • El disco no es persistente. Todo lo que se escriba en CSV dentro del servidor se pierde en el siguiente deploy o reinicio. Lo que deba sobrevivir tiene que ir a Neon.
  • Los datos personales cargados en el servidor quedan en un datos.csv compartido entre visitantes: el aislamiento por cuenta está pendiente. Por eso el repo es privado y los CSV personales no viajan.
  • Los medios pesados no están en el repo: las fotos se regeneran con bajar_fotos_publicas.py y el audio de canales queda solo en local.

7. Si algo falla

  • Error al importar psycopg2: revisar que psycopg2-binary esté en requirements.txt (ya está).
  • La app arranca pero no calcula: falta algún CSV. En un clon nuevo se crean vacíos con python preparar_datos.py, que INICIAR.cmd ya llama antes de arrancar.
  • 404 en /lab: es intencional, esa plantilla no se publica.
  • Falla la función de circuitos excluyentes: falta razgos.xlsx, que no está en el proyecto. No se reemplazó por una aproximación.

8. La diferencia con correr en local

En local, INICIAR.cmd levanta Waitress con 8 hilos y puerto 5000, sin depender de internet. En Render manda Gunicorn y el puerto lo decide la plataforma. El código es el mismo: solo cambia quién lo sirve y dónde viven los datos.

Nota: el repositorio es privado, así que este manual describe el procedimiento, no ofrece un enlace público al código.
